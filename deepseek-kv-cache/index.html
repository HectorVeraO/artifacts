How DeepSeek's context cache works

Prefix caching on disk, on by default: no code, no cache_control, no TTL. A cache-hit input token costs 50 times less than a miss, and in the session measured below 99.50% of input tokens hit.

01

The matching rule

A request hits only when everything it sends begins with a prefix that already exists on disk as a persisted cache unit.

Matching is on the token prefix, not on the conversation and not on a request identifier. A cache unit is written in three situations:

  1. a
    At every request boundary One unit is persisted where the user input stops, another where the model output stops. Send the same opening text again and both units are found.
  2. b
    On a prefix shared across requests When several requests open with the same tokens, DeepSeek persists that common prefix as its own unit. This is what keeps a system prompt and a tool catalogue warm from one session to the next.
  3. c
    At fixed token intervals inside long text Long inputs and long outputs get units written as they grow, so a prefix is never left permanently uncacheable just because no request ended there.

What the rule does in practice

A+B then A+B+C
hits on A+B. Only C is billed as new input.
A+B then A+C
misses from the first token that differs. The request still teaches the cache that A is shared.
A+D afterwards
hits on A, because the previous miss registered A as a common prefix.

The miss does not throw work away: A+C is persisted at its own end, so a later A+C+E hits A+C. What never happens is a partial match inside a request. Either the prefix matches to the end of a persisted unit, or those tokens are new.

02

What a session looks like

Each tool-call turn appends a thin slice of new tokens to a prefix that stays cached, so the expensive part of the bar stops growing.

03

Measured on a real session

One root OpenCode session on deepseek-flash spent $0.2398 to move 36.0M tokens, and 99.50% of the input tokens were cache hits.

Figures come from the session's own usage record and from the provider-reported cost. Prices are the off-peak rates: $0.003 per 1M cache-hit input, $0.15 per 1M miss input, $0.60 per 1M output, with reasoning billed as output.

Output tokens: 92,521 generated plus 84,189 reasoning, both billed at the output rate.

Where each cent went

  • Cache-hit input $0.1070 · 44.6%
  • Output plus reasoning $0.1060 · 44.2%
  • Cache-miss input $0.0268 · 11.2%

The three lines add up to the $0.2398 the provider reported, to the cent. That is how the price model was confirmed: no separate charge appears for writing the cache, reasoning bills at the output rate, and everything read back gets the same discount.

The cache was already warm at the first request. Session start read 12,544 tokens from cache against 5,288 new ones, because a previous session had persisted the same system prompt. Only a first session with nothing on disk pays the miss price on its prompt.

04

What breaks the cache

Changing anything at the front of the request invalidates every unit written after the first token that differs.

In an agent session the front of the request is assembled, not typed. That is where a cache gets lost:

  • Editing an instruction file the agent loads. An instruction file, a rules file or a skill body sits near the start, so every token after it counts as new.
  • Adding or removing a skill. The skill catalogue lives in the system prompt, so the prompt changes even when the skill is never used.
  • Restarting an MCP server. The tool list is part of the prompt, and a restart can change it.
  • Switching agent or model mid-session. A different system prompt is a different prefix, so the cached units no longer line up.
  • Running /reload. Config and prompt are rebuilt from disk.
  • Context compaction. History is replaced by a summary, and the summary is not the text that was cached.

A full invalidation on a 40k-token context costs $0.012 at peak, at $0.30 per 1M miss tokens, or $0.006 off-peak. The same 40k read from cache costs $0.00024 at peak. A handful of invalidations in a session is noise; a reload inside a loop is not.

What does not break it

  • Appending tool output. New tokens extend the end of the prefix; the cached part stays where it was.
  • A new user turn. Same reason: the conversation grows to the right.
  • A subagent opening a fresh session. It starts its own prefix and leaves the parent's cache untouched.
05

Where the money actually goes

In the measured session, cached input and output cost almost the same amount, $0.1070 against $0.1060, but they behave differently. Cached input grows with how long the session runs and is paid at the cheapest rate on the price list; output grows with what the model writes and what it reasons through, and you decide both. Peak pricing beats every caching trick: two UTC windows on weekdays (01:00-04:00 and 06:00-10:00) double every line, and the same session at peak would have cost $0.4796. Running a long job off-peak is worth more than any cache optimisation inside it.
